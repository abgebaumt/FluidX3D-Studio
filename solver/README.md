# Solver side

The C++ files in this folder are copied to `<fluidx3d>/src/` by
`scripts/install-solver.js`. They are the only FluidX3D code that FluidX3D
Studio brings along.

| File | Contents |
|---|---|
| `json.hpp` | Minimal, read-only JSON parser. Header-only, C++17, no dependencies beyond the standard library. |
| `mesh_seal.hpp` | Runtime sealing of thin walls: triangle rasterization, morphology, flood fill, transfer into `lbm.flags`. Header-only, C++17. |
| `setup_config.cpp` | A `main_setup()` that builds the complete scene from a setup config. Entirely wrapped in `#ifdef GUI_CONFIG_SETUP`. |

`CONTRACT.md` is binding: section 1 (schema), section 2 (derived quantities),
section 5 (these files) and section 8 (sealing). If anything changes there, it
must be updated here and in `web/js/derive.js` at the same time.

## Installing and removing

```
npm run install-solver     # copy, guard setup.cpp, extend vcxproj
npm run uninstall-solver   # revert everything
```

`mesh_seal.hpp` must be copied along with the others: `SOLVER_FILES` in
`scripts/install-solver.js` and `scripts/uninstall-solver.js` holds the list,
and `FluidX3D.vcxproj` needs a `<ClInclude Include="src\mesh_seal.hpp" />` for
it next to the one for `json.hpp`. Without the entry in `SOLVER_FILES`,
`setup_config.cpp` cannot find the header and the build fails.

Both scripts are idempotent. They back up every file they touch once to
`data/backup/<name>.orig` and mark every change to files they do not own with
`// >>> fluidx3d-studio` … `// <<< fluidx3d-studio` or
`<!-- >>> fluidx3d-studio -->` … `<!-- <<< fluidx3d-studio -->`, so that
uninstalling removes exactly those lines again.

The installer does **not** define `GUI_CONFIG_SETUP`. The macro comes from the
`defines.hpp` generated by the server (CONTRACT.md section 4). Without it,
`setup_config.cpp` is empty and the hand-written `main_setup()` from `setup.cpp`
stays active — so a build without the studio keeps working.

`make.sh` compiles `src/*.cpp` by wildcard and needs no change.

## Invocation

```
bin/FluidX3D.exe --config <absolute path to the setup JSON>
bin/FluidX3D.exe 0 --config <path>      # device 0, then the config
```

`main_setup()` extracts the pair `--config <path>` from `main_arguments` and
removes it before FluidX3D interprets the remaining arguments as OpenCL device
IDs. If `--config` is missing, `config.json` next to the executable is tried; if
that does not exist either, the solver aborts with an error message.

According to the schema, object files are relative to `data/`. Since the config
lives in `data/setups/`, `data/` is its grandparent directory; in addition, the
config's own folder and the executable's folder are searched as fallbacks.
Absolute paths are used as they are.

## From config to scene

**Domain, resolution, units.** `resolution(float3(lx, ly, lz), target_vram_mb)`
from FluidX3D yields the grid — exactly this formula is replicated by the
frontend. Then `units.set_m_kg_s(Nx, u_lbm, 1, size_m[0], velocity_ms, density_kgm3)`,
which makes a cell `size_m[0]/Nx` metres in size. From that, `dt`, `nu_lbm` and
`tau` follow as in CONTRACT.md section 2. At startup, grid, cell size, time
step, Reynolds number, `nu_lbm` and `tau` are printed via `print_info`, so they
can be compared with what the GUI displays.

**Objects.** `read_stl` reads the file unscaled and unrotated (STL units are
metres). Then, in this order:

1. scale — `longest_edge_m` sets the longest edge of the *unrotated*
   bounding box to the value, `scale` multiplies directly; followed by the
   conversion from metres to cells,
2. rotate about the object's own bounding-box centre, `Rz(yaw)·Rx(pitch)·Ry(roll)`,
3. move the bounding-box centre to `position_frac · N`,
4. voxelize,
5. seal, if `sealing.mode` is not `"off"` (see below).

`enabled: false`, an unknown `type`, a missing file or an unusable scale lead
to a warning and the object is skipped — never to an abort.

If an object has `source_file` set and `file` points to something else,
`source_file` is loaded. This concerns legacy setups from the old approach, in
which the server precomputed a thickened STL for **one** cell size and pointed
`file` at it: at any other resolution that file is coarser than the original
and would only cost detail. `sealing.sealed_file` is not evaluated.
`validateObject()` in `web/js/schema.js` performs the same substitution; the
solver does it for setup files that have never passed through the new
frontend. If `source_file` is missing or cannot be resolved, `file` is used —
this is never an error.

**Inflow and boundaries.** The velocity vector is built from magnitude, azimuth
and elevation as
`u · (sin(az)·cos(el), cos(az)·cos(el), sin(el))`, i.e. `+y` at 0°/0° and
`+z` for positive elevation. Per box face: `equilibrium` and `open` →
`TYPE_E`, `solid` → `TYPE_S`, `periodic` → the cell is left untouched (FluidX3D
is already periodic there).

**Visualization.** `modes` is OR-ed into `VIS_FLAG_SURFACE`, `VIS_FLAG_LATTICE`,
`VIS_FIELD`, `VIS_STREAMLINES`, `VIS_Q_CRITERION`; an empty list falls back to
`VIS_FLAG_SURFACE` so the image is not empty. `visualization.q_criterion`,
`.u_max` and `.background`, on the other hand, are compile-time constants and
live in the generated `defines.hpp`.

**Moving objects.** With `motion.type == "rotate"` the mesh is kept in memory.
The angular velocity in LBM units is `units.omega(rpm · 2π/60)` — radians per
time step. The time loop always runs up to the next due re-voxelization, then
rotates the mesh further by `omega · elapsed steps` and re-voxelizes it with
`rotational_velocity = axis · omega`; this also clears the old cells in the
bounding box. A different `revoxelize_interval` per object is honoured
individually. Without the `MOVING_BOUNDARIES` extension there is a warning, but
the run still works.

**Run.** With `GRAPHICS` and without `INTERACTIVE_GRAPHICS`, render mode runs:
`duration_s · fps` frames, the camera orbiting from `azimuth_from_deg` to
`azimuth_to_deg` (constant `azimuth_from_deg` for `type: "fixed"`), output to
`bin/export/<name>/`; `camera.distance` is the field of view that
`set_camera_centered` expects. Otherwise simply `lbm.run()` with FluidX3D's
interactive controls.

## Sealing — `mesh_seal.hpp`

### Why

FluidX3D's `voxelize_mesh` casts one ray per cell column and stores the hit
distances as integers (`ushort distances[64]`, `kernel.cpp` from line 2271
onwards). If a wall is thinner than one cell, its front and back land on the
same integer value, the inside/outside state flips twice in the same step, and
the wall **disappears entirely** — not partially. A perfectly watertight STL
loses its 2 mm flap at 5.88 cm cell size. This is a resolution problem, not a
mesh problem; STL repair does not help.

### Where it happens

At **runtime**, at exactly the resolution that is being simulated. Previously
the server generated a second, thickened STL for this. It was computed for a
fixed cell size and frozen: anyone who raised the VRAM target afterwards got a
finer simulation with coarser geometry — i.e. less detail than the original.
That is exactly why sealing now lives in the solver.

### Procedure

`mesh_seal::seal_mesh_into_flags(lbm, mesh, TYPE_S, mode, close_holes, min_thickness, name)`

1. **Sub-grid** — bounding box of the already scaled, rotated and placed mesh
   in grid coordinates, plus a margin of `max(close_holes, min_thickness-1)+2`
   cells, clamped to the domain. Only this block is processed. For a 25 m model
   in a 60 m box that is a few million cells instead of ~190 million — which is
   why the step is affordable.
2. **Shell** — every triangle is rasterized into the cells it overlaps
   (separating-axis test of triangle against axis-aligned box, 13 axes). This is
   the actual fix: a face occupies cells regardless of its thickness. Touching
   counts as overlapping, so that a face lying exactly on a cell boundary does
   not fall through the grid.
3. **Close holes** (`close_holes` = n > 0) — morphological closing with radius
   n: dilate, then erode. Seals openings up to 2n cells wide.
4. **Fill** (`mode: "fill"`) — flood fill from the border of the sub-grid
   through all empty cells; everything not reached is interior and becomes
   solid.
5. **Thicken** (`min_thickness` > 1) — shell mode only; a filled body is solid
   anyway.
6. **Transfer** — the mask is **OR-ed** into `lbm.flags`. Existing flags of
   other objects are never cleared.

`mode: "shell"` leaves the body hollow, `"fill"` makes it solid. For a body in
a flow only the wetted surface matters, so `"fill"` is the safe recommendation;
`"shell"` is there for intentional internal cavities.

### Order in the setup

Two conditions determine where this happens in `main_setup()`:

* **after** all `voxelize_mesh_on_device()` calls for the static objects — this
  call reads `lbm.flags` back from the device and would overwrite sealing
  written in between. The meshes are therefore kept alive until then and only
  freed afterwards;
* **before** the inflow loop — it only sets `u` on cells that are not
  `TYPE_S`. If sealing came afterwards, the new solid cells would carry the
  inflow velocity and, with `MOVING_BOUNDARIES`, act as a moving wall.

### Output

One line per sealed object:

```
Sealing "Fuselage": sub-grid 164 x 164 x 50 = 1344800 cells, shell 18904,
filled 22329, solid 41233 (9871 new), hull closed, 0.42 s
```

`… new` are the cells that FluidX3D's own voxelization had **not**
set — this is the number that justifies the step. `hull open` means the flood
fill escaped: nothing was filled in that case, and `close_holes` should be
raised.

### Limitations

* **Moving objects are not sealed.** `motion.type: "rotate"` with `rpm != 0` is
  re-voxelized over and over during the run; sealing on every re-voxelization
  would be too expensive. A one-time notice is printed for this. (`"rotate"`
  with `rpm == 0` counts as static and is sealed.)
* The sub-grid is limited to 64 million cells (`MAX_SEAL_CELLS`). Above that,
  sealing is skipped with a warning; at that point it is more likely a wrong
  VRAM target than a genuine request.
* Rasterization claims every cell it touches, ray casting only cells whose
  centre lies inside. A sealed body is therefore about one cell layer thicker
  at the surface than a purely ray-cast one. For a body that is many cells
  thick, that is the price for the thin parts existing at all.
* If the object reaches the edge of the domain, outside cannot be told from
  inside there; a warning is printed.
* Memory: 1 byte per cell for the mask, 1 more for the morphology, 4 bytes per
  cell for the flood-fill queue — never an object per cell. Everything is freed
  again after sealing.

The algorithms are ported one-to-one from `server/voxel-seal.js`, the tested
reference implementation.

## json.hpp

```cpp
json::Document doc = json::parse_file(path);   // or json::parse(text)
if(!doc.ok()) print_error(doc.error);          // message with line and column
const json::Value& j = doc.root;

const float x = j["domain"]["size_m"][0].as_float(36.0f);
const uint  n = j["domain"]["target_vram_mb"].as_uint(4000u);
const string s = j["name"].as_string("setup");
const bool  b = j["objects"][0]["enabled"].as_bool(true);
for(std::size_t i=0u; i<j["objects"].size(); i++) { ... }
```

Objects, arrays, strings with all escapes (including `\uXXXX` and surrogate
pairs), numbers with exponents, and `true`/`false`/`null` are supported. Every
path that leads nowhere returns a shared null value, and every `as_*()` takes a
fallback value — so a missing entry cannot crash the solver. `exists()`
deliberately does not distinguish between "missing" and "is null". Numbers are
parsed independently of the locale, a UTF-8 BOM at the start of the file is
skipped, and the nesting depth is limited to 64.

## Limitations

* Schema 1 only knows `type: "stl"`, and only binary STL files.
* `sealing.cell_m`, `sealing.sealed_file`, `sealing.computed_at` and
  `sealing.stats` are legacy fields from the server-side approach. The solver no
  longer reads them; only `mode`, `close_holes` and `min_thickness` matter.
* Multiple GPUs are not controlled from the config; the device IDs on the
  command line remain responsible for that.
* `visualization.q_criterion`, `.u_max`, `.background`, velocity set, precision
  and extensions are compile-time decisions and only change through a rebuild.
